# Contributing

OpenWrist should stay understandable for humans, even though much of the code is
written with AI assistance. These rules apply to every contribution, from
humans and agents alike.

## AI-assisted contributions

OpenWrist is built with AI, for people. Using AI tools is welcome. Handing your
judgment over to them is not.

**You are responsible for your contribution.** Whatever tool wrote the code,
you submit it, so you vouch for it.

Accepted:

- Code written with help from an AI assistant that you have read, understood
  and tested.
- AI help with research, reviews, documentation or commit messages, checked
  by you.

Not accepted:

- **Fully automated or agentic contributions.** Pull requests, issues or
  comments created by an agent or bot without a human in the loop.
- **Unreviewed "vibe-coded" code.** If you cannot explain a change line by
  line, it is not ready.

Before you open a pull request, ask yourself:

- Can I explain what every line does and why it is there?
- Could I fix a bug in this code without asking the AI?
- Did I run it and check the behavior myself?

If the answer is no, keep working on it. Reviewers may ask you to walk them
through your change; "the AI wrote it" is not an answer.

Mark AI involvement in commits with a `Co-Authored-By:` trailer, so the
history stays honest.

### Talking to each other

Issues, pull request descriptions, review comments and discussions are
conversations between people. **Write them yourself.**

- Machine translation is fine. Write in your own language and translate it,
  if that is easier for you.
- Everything else comes from you: the thoughts, the arguments, the
  questions. Do not post text generated by an AI.
- Nobody is judged for grammar, spelling or language skills. We are all just
  human. A clumsy sentence you wrote is worth more than a polished one you
  did not.

Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md).

## Commits

**One commit, one intent.** Someone reading `git log` should understand what
was added and why without opening the diff.

- Format: [Conventional Commits](https://www.conventionalcommits.org/)
  - `feat:` new behavior
  - `fix:` bug fix
  - `refactor:` restructuring without behavior change
  - `docs:` documentation only
  - `test:` tests only
  - `build:` dependencies, Gradle, CI
  - `chore:` anything else that does not affect behavior
- Optional scope: `feat(install): show download progress on the watch`
- Subject line in the imperative mood, at most 72 characters.
- The body explains **why**, not what. The what is in the diff.
- Never mix refactoring and behavior changes in one commit.
- Every commit builds and passes the tests (`./gradlew test`), so `git bisect`
  works.
- Commits written with AI help carry a `Co-Authored-By:` trailer (see
  above).

Example:

```
feat(install): show download progress on the watch

Large downloads left the screen looking frozen. A progress indicator
makes clear that the install is still running.
```

## Code

- `./gradlew ktlintCheck detekt` without warnings (set up with the first module).
- Every module has a package comment that describes its job in a few
  sentences.
- Public types and functions have KDoc comments (`/** */`).
- Comments explain why. The code itself should show what it does.
- No abstractions in advance: an interface is introduced when the second
  implementation exists, not before.

## Language

English for code, comments, commits and documentation.

## Documentation

- When the architecture changes, `docs/architecture.md` changes in the same
  commit.
- Larger decisions (library, format, structure) get an ADR in
  `docs/decisions/`. Template: [`0000-template.md`](docs/decisions/0000-template.md).
